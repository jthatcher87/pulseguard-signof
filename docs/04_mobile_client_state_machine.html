  1. Executive Overview & State Architecture

1.1 Technical Stack & Execution Environment

The PulseGuard mobile client is engineered as a zero-knowledge, high-assurance digital health and exposure notification application:

  • PRESENTATION & BUSINESS LOGIC LAYER | Built natively using Flutter / Dart, compiled Ahead-Of-Time (AOT) to native ARM64 machine code. There is no JavaScript runtime, no WebAssembly translation layer, and no browser Document Object Model (DOM) attack surface.
  • STATE ARCHITECTURE PATTERN: Implemented via Riverpod (StateNotifier / AsyncNotifier) enforcing unidirectional data flow, explicit state immutability, compile-time provider safety, and deterministic testability.
  • HARDWARE ROOT-OF-TRUST: Cryptographic operations interface directly with platform hardware security modules—the Apple Secure Enclave Processor (SEP) on iOS and Android StrongBox / Keymaster on Android.
  • TRIPLE-LEDGER MEMORY & PERSISTENCE ISOLATION: The local persistence layer is physically and cryptographically partitioned into three distinct SQLite databases encrypted with SQLCipher (AES-256-GCM):
  1. Ledger A (ledger_a_medical.db): Medical History & Diagnostic Vault, encrypted under hardware key K_{health}. Contains LOINC diagnostic codes, qualitative results, specimen dates, detached lab signatures, and negative anchors. Contains zero encounter tokens, zero credentials, and zero PII.
  2. Ledger B (ledger_b_encounters.db): Ephemeral Encounters Vault, encrypted under hardware key K_{tokens}. Contains dynamic rotating beacon tokens, pathogen-scoped burn states, local-only behavioral tags, and received advisories. Contains zero medical history and zero credentials.
  3. Ledger C (ledger_c_auth.db): EHR Connection & Refresh Token Vault, encrypted under hardware key K_{auth}. Stores encrypted OAuth refresh tokens and provider FHIR endpoints strictly when automated sync is opted in. Contains zero clinical data and zero encounter tokens.
  • Absolute Relational Decoupling: Zero foreign keys, zero relational joins, and zero indices exist across Ledgers A, B, and C. Any correlation occurs exclusively in volatile RAM during runtime execution and is purged immediately with binary zeros (memset_s).

Architectural Rules:

  1. Independent Key Derivation: K_health, K_tokens, and K_auth are derived along non-converging derivation paths from hardware roots of trust. Compromising one key provides zero mathematical advantage against the others.
  2. Zero Persistent Joins: There are no foreign keys, relational indices, or join tables linking Ledgers A, B, and C.
  3. Volatile-Only Memory Correlation: Any correlation between clinical windows and encounter tokens occurs strictly in volatile RAM and is scrubbed immediately via memset_s.
  4. Ledger C Opt-Out Wipe: If the user disables automated EHR sync, Ledger C is overwritten with binary zeros (memset_s) and K_auth is permanently revoked from the hardware Secure Enclave.
  1. Domain 1: App Lifecycle, Physical Security & Biometrics

2.1 State Definitions

  • UNINITIALIZED: App installed but no hardware keys derived; onboarding incomplete; BIP-39 mnemonic seed phrase ungenerated.
  • LOCKED: Cryptographic master keys evicted from volatile RAM; UI view buffers purged; biometric/PIN barrier presented.
  • AUTHENTICATED: Active session; K_{health} and K_{tokens} handles available in volatile memory; UI fully operational.
  • GRACE_SUSPENDED: App transitioned to background with "Zero-Tolerance App Lock" disabled; 15-second in-memory countdown running.
  • OBSCURED_GAZEGUARD: Foreground sensitive view actively shielded by high-depth blur due to shoulder-surfer detection or device tilt.
  • COOLDOWN_LOCKED: Hardware monotonic PIN rate-limit penalty active (1 to 3.5 minutes); credential inputs disabled.
  • WIPED_SELF_DESTRUCT: Permanent terminal state; 11 failed PIN attempts registered; Secure Enclave keys revoked; databases zeroed.

2.2 Lifecycle & Security Directives

  1. Zero-Tolerance App Lock Settings:
  • Controlled via an in-app setting labeled "Zero-Tolerance App Lock" (Default: ON).
  • When ON: Transitioning to AppLifecycleState.paused or inactive triggers instant volatile memory zeroization and forces state transition to LOCKED with zero grace period.
  • When OFF: Transitioning to paused starts an ephemeral 15-second hardware monotonic timer. Resuming within 15 seconds returns to AUTHENTICATED. At t = 15.001s, memory is zeroed and state transitions to LOCKED.
  1. Biometric Failure & Tiered Hardware Lockout Schedule:
  • Biometric Threshold: Exactly 3 consecutive failed biometric/passkey assertions disables biometrics and enforces PIN Entry Only.
  • Monotonic PIN Lockout Counter (Apple SEP / Android StrongBox):
  • Attempts 1–4: Immediate retry permitted with haptic error feedback.
  • Attempt 5: Enforces hardware cooldown of 00:01:00 ("Too many failed attempts. Retry after cooldown period.").
  • Attempt 6: Cooldown resets to 00:01:30 ("Retry after cooldown period. *WARNING: 5 Attempts remain until application and local app data is destroyed permanently.").
  • Attempt 7: Cooldown resets to 00:02:00 ("Retry after cooldown period. *WARNING: 4 Attempts remain until application and local app data is destroyed permanently.").
  • Attempt 8: Cooldown resets to 00:02:30 ("Retry after cooldown period. *WARNING: 3 Attempts remain until application and local app data is destroyed permanently.").
  • Attempt 9: Cooldown resets to 00:03:00 ("Retry after cooldown period. *WARNING: 2 Attempts remain until application and local app data is destroyed permanently.").
  • Attempt 10: Cooldown resets to 00:03:30 ("Retry after cooldown period. ‼️CRITICAL WARNING ‼️ This is the final attempt before all locally encrypted enclave data is permanently deleted and scrubbed. ⚠️ IMPORTANT: Once scrubbed the data cannot be recreated or retrieved from memory or storage.").
  • Attempt 11 (Terminal Execution): Permanent cryptographic self-destruct. Hardware keys K_{health}, K_{tokens}, and K_{auth} are revoked and deleted from the Secure Enclave / StrongBox. All SQLite database files are overwritten with zeros (memset_s) and unlinked. The application resets to UNINITIALIZED.
  1. Mandatory BIP-39 Recovery Onboarding:
  • Generating and recording the 12-word recovery mnemonic is strictly mandatory during initial setup.
  • User cannot enter the app until they successfully complete a randomized 3-word challenge (e.g., "Select Word #3, Word #7, and Word #11").
  1. OS-Level Screen Shielding & Dev Mode:
  • In production builds, WindowManager.LayoutParams.FLAG_SECURE (Android) and applicationWillResignActive opaque window masking (iOS) are 100% active, preventing screenshots, screen recordings, and task-switcher snapshots.
  • Debug/Internal builds feature a gated "Dev Mode / God Status" toggle to disable shielding strictly for QA bug logging, physically stripped from production binaries via #if DEBUG compiler flags.
  1. Neural GazeGuard (Edge AI Shoulder-Surfer Defense):
  • Activation: Remains actively monitoring via front-camera NPU whenever sensitive medical views (Ledger A clinical records, incoming exposure advisories) are rendered.
  • Trigger: If an auxiliary face or acute tilt angle is detected, the UI blurs into frosted glass within <80ms.
  • Deactivation: Strictly requires Biometric unlock or PIN re-entry. Moving the secondary face out of frame will not auto-clear the blur.
  1. Domain 2: Proximity Exchange & Encounter State Machine

3.1 State Definitions

  • IDLE: Radio and optical scanners dormant; awaiting user proximity trigger.
  • BEACON_BROADCASTING: Host mode active; displaying dynamic 2D optical QR beacon rotated every 30 seconds via HMAC-SHA256(EMS, epoch).
  • BEACON_SCANNING: Camera HUD active; scanning peer QR beacon (<300ms capture).
  • P2P_HANDSHAKE_MUTUAL: 1-on-1 NFC tap (Bump to Pair) or optical bidirectional pairing; executing ephemeral Curve25519 ECDH key agreement.
  • POST_CHECKIN_ROUTING: Handshake complete; executing user-configured post-check-in workflow.
  • COMMITTED_LEDGER_B: Ephemeral session token, timestamps, and context written to hardware-encrypted Ledger B.
  • VENUE_SESSION_ACTIVE: User checked into an active group/venue event; awaiting auto-expiration or manual departure.

3.2 Proximity & Bounding Directives

  1. User-Configurable Post-Check-In Flow:
  • Configurable under "Check-In Preferences" with three selectable modes:
  • Mode A (Fast Auto-Dismiss): Instant haptic confirmation \to immediate dismissal to Home Screen. Tags default to UNSPECIFIED in Ledger B (user can edit later).
  • Mode B (Immediate Modal — Default): Quick 2-tap bottom sheet with barrier/role pills, auto-dismissing after 10 seconds if untouched.
  • Mode C (Delayed Reminder): Dismisses instantly, but schedules a silent local notification 1–2 hours later prompting optional notes.
  1. Calendar-Day Temporal Modeling (1-on-1):
  • Time-of-day hours and minutes are discarded for clinical exposure evaluation. Encounters are anchored strictly to the full calendar date (YYYY-MM-DD). This matches biological incubation timelines and prevents forensic time-triangulation.
  1. Venue & Overnight Event Bounding:
  • Single-day events (e.g., Saturday 2:00 PM – 10:00 PM) are bounded to that calendar date.
  • Overnight events spanning midnight (e.g., Saturday 10:00 PM – Sunday 4:00 AM) span both dates and anchor the exposure evaluation to the event conclusion date (Sunday). This guarantees that attendees who depart before midnight remain covered by lookback calculations if transmission chains continued through the event's conclusion.
  1. Domain 3: Clinical Ingestion & Triple-Ledger Synchronization

4.1 State Definitions

  • CLINICAL_IDLE: No active laboratory ingestion; monitoring scheduled screening cadences.
  • AUTH_FLOW_ACTIVE: System secure webview active (ASWebAuthenticationSession / Custom Tabs); user authenticating with MyChart / Quest.
  • FHIR_INGESTION_RAM: Raw FHIR JSON or SMART Health Card JWS payload resident in volatile RAM.
  • SURGICAL_PII_PURGE: Volatile RAM parser extracting non-PII attributes and overwriting PII with zeros (memset_s) in <10ms.
  • SYPHILIS_ADJUDICATION_GATE: Active screening for treponemal vs nontreponemal markers; checking prior treatment history.
  • ATOMIC_DISAGGREGATION: Splitting multi-panel results; committing negatives to anchors and positives to clinical episodes.
  • COMMITTED_LEDGER_A: Clinical record, LOINC codes, and detached lab signatures committed to Ledger A under K_{health}.
  • LEDGER_C_PURGE: Opt-out ceremony executing DoD-grade zero-fill memory wiping of Ledger C and revoking K_{auth}.

4.2 Ingestion & Clinical Adjudication Directives

  1. Triple-Ledger Architecture & Ledger C Opt-In Model:
  • Automated background sync is opt-in, supported by an interactive educational infographic explaining credential storage.
  • If enabled, OAuth refresh tokens and provider endpoints are stored in Ledger C (ledger_c_auth.db), encrypted under dedicated hardware key K_{auth}. Zero foreign keys connect Ledger C to Ledgers A or B.
  • If the user opts out, a warning dialog is displayed. Upon confirmation, Ledger C database pages are completely overwritten with binary zeros (memset_s) and unlinked, and K_{auth} is revoked from the hardware Secure Enclave.
  1. Multi-Panel Atomic Disaggregation:
  • In a single atomic transaction, all negative results in an ingested panel are committed to negative_test_anchors in Ledger A (empowering Smart Truncation).
  • All verified positive results create active entries in clinical_episodes and launch the outbound notification workflow.
  1. Indeterminate / Inconclusive Results Policy:
  • Results marked INDETERMINATE, EQUIVOCAL, or INCONCLUSIVE are committed to Ledger A with guidance ("Inconclusive — re-testing recommended in 14 days"), but strictly block outbound exposure manifest generation.
  1. Dual-Marker Syphilis Adjudication Protocol (Preventing False Positives):
  • Treponemal-Only Filter: Treponemal antibody tests (TP-PA, EIA) measure lifetime antibodies and can remain positive for life; a treponemal test alone can NEVER trigger an exposure broadcast.
  • Quantitative RPR Requirement: Diagnosis requires a quantitative nontreponemal titer (RPR / VDRL, LOINC 20507-0).
  • The "Prior Treatment History" Triage Gate:
  • When no baseline exists in Ledger A, the app asks: "Have you received penicillin or antibiotic treatment for Syphilis in the past?"
  • If NO (Never Treated): Classified as new active infection; authorizes outbound lookback notification workflow.
  • If YES (Previously Treated): Explains the serofast state. Unless the user confirms their provider verified an active reinfection (e.g., a 4-fold / two-dilution titer increase from 1:2 to 1:8), the broadcast is aborted, and the titer is logged as the local Baseline Serofast Anchor in Ledger A to prevent future false alarms.
  1. Domain 4: Outbound Exposure Broadcast & Inbound Advisories

5.1 State Definitions

  • OUTBOUND_PREVIEW: Presenting shame-free clinical window confirmation card; zero partner counts displayed.
  • POW_SOLVING: Computing client-side Hashcash Proof-of-Work challenge (~2 seconds CPU load).
  • JITTER_QUEUED: Manifest held in local encrypted background queue with 1–4 hour randomized delay.
  • DISPATCHING_OHTTP: Transmitting encapsulated Binary HTTP payload to public relay via OHTTP Gateway / Tor proxy.
  • BROADCAST_COMPLETE: Hashing complete; tokens marked as BURNED for reported pathogen in Ledger B; dignified confirmation rendered.
  • ADVISORY_UNREAD: New matching hash identified locally during background sync; notification queued or displayed.
  • ADVISORY_REVIEWED: User biometrically unlocked app and inspected pathogen, timeframe, and clinical testing window.
  • ADVISORY_ACTION_LOGGED: User recorded local action (PEP/Doxy-PEP sought, test scheduled, clinic visited).
  • ADVISORY_ARCHIVED: Case resolved; retained locally in Ledger B for personal audit.

5.2 Broadcast & Notification Directives

  1. Shame-Free Outbound Confirmation Card:
  • NO personal partner counts ("Notifying X people") or token counts are ever displayed.
  • Framed strictly around the CDC biological transmission window (e.g., "Covering exposures within the CDC-recommended 60-day clinical window: July 15 – August 28").
  • Post-broadcast confirmation displays:

"The relative encounters have been notified under our explicit zero-PII guarantee."

  1. Dual-Mode Outbound Transmission Jitter:
  • Default Mode: Uploads default to randomized transmission jitter (1 to 4 hours) dispatched via an encrypted background task to neutralize network correlation attacks.
  • Emergency Override: User can toggle "Send Immediately (Bypass Delay for Urgent Partner Prophylaxis)" if an encounter occurred within the critical 72-hour window for PEP or Doxy-PEP.
  1. Inbound Advisory Notification Timing & Quiet Hours:
  • Users define custom quiet hours (Default: 10:00 PM to 08:00 AM).
  • Routine matches discovered during quiet hours are held in local memory and dispatched at 8:01 AM.
  • Urgent Prophylaxis Exception: High-urgency exposures (e.g., HIV exposure <72h requiring PEP) bypass the quiet window.
  1. Local Ambient Camouflage Notifications (Zero-Bubble Rule):
  • Critical alerts use discreet notification architecture: zero lock-screen pop-up bubbles and zero pathogen names.
  • Rendered using local OS notification APIs as either Mode 2 (Simulated Patient Health Portal Notice) or Mode 3 (Silent In-App Badge Dot Only).
  • Tapping the notification requires immediate Biometric or PIN authentication before disclosing clinical details.
