﻿PulseGuard Stateless Public Relay Architecture & Deployment Guide

1. System Overview & Threat Model

The PulseGuard Stateless Public Relay functions as a zero-knowledge, append-only public bulletin board for anonymous exposure notification manifests. In accordance with PulseGuard's zero-PII cryptographic posture, the relay server is architecturally incapable of identifying which users or physical devices published a manifest or which devices downloaded and matched a manifest locally.

Core Security & Privacy Invariants:

1. Network Anonymity (RFC 9292 / RFC 9458): The OHTTP Gateway proxy and Target Relay server are deployed on isolated cloud infrastructures. The Gateway terminates client IP addresses but cannot decrypt payload contents. The Target Relay decrypts payloads but only communicates with the Gateway.

2. Zero Server Relational Graph: The relay stores no relational graphs, no user accounts, no device identifiers, no push tokens, and no geolocation coordinates.

3. Immutable Ephemeral Retention: All stored manifests are strictly time-bounded (14 to 30 days) matching pathogen biological windows, after which memory and persistent keys automatically self-destruct via TTL eviction.

4. Denial-of-Service & Anti-Troll Shield: Automated bot floods and griefing submissions are neutralized through a multi-tier defense: Hashcash Proof-of-Work (minimum 20-bit difficulty), detached JWS laboratory verification, and hardware-bound rate-limit cooldowns.

2. Oblivious HTTP (OHTTP) Gateway & Target Separation

PulseGuard adheres to the IETF standards for Oblivious HTTP:

  • RFC 9292: Binary Representation of HTTP Messages (message/bhttp).
  • RFC 9458: Oblivious HTTP protocol specification.
  • RFC 9180: Hybrid Public Key Encryption (HPKE).

    • Key Configuration Lifecycle (GET /ohttp-keys):

    The relay target publishes an active HPKE key configuration:

  • KEM: DHKEM(X25519, HKDF-SHA256) (Identifier: 0x0020)
  • KDF: HKDF-SHA256 (Identifier: 0x0001)
  • AEAD: AES-128-GCM (Identifier: 0x0001) or ChaCha20Poly1305 (Identifier: 0x0003)

    • The client fetches /ohttp-keys, packages its POST /manifest/publish request into Binary HTTP format, encapsulates it with the relay's public key, and transmits it to the OHTTP Gateway. The Gateway forwards the binary blob to the target relay over an internal mutual-TLS (mTLS) link.

    3. Ingestion Pipeline & Verification Engine

    When the target relay receives an unwrapped POST /manifest/publish request:

    [ Ingest Request ]

    [ Step 1: Proof-of-Work Verification ]

    → Check Header: X-PulseGuard-PoW

    → Validate Hashcash format (1:bits:date:resource:ext:salt:counter)

    → Verify SHA-1 / SHA-256 hash has >= 20 leading zero bits (~1,048,576 iterations)

    → Verify timestamp within +/- 15 minutes of server UTC clock

    → Check Replay Cache in Redis (SETNX pow: EX 1800) -> If duplicate: 403

    [ Step 2: Schema & Hash Array Validation ]

    → Validate 1 <= count(hashes) <= 5000

    → Validate all hashes are strictly 64 hexadecimal characters (BLAKE3)

    → Validate LOINC pattern (e.g., ^[0-9]{3,5}-[0-9]$)

    [ Step 3: Laboratory Signature & Anti-Troll Cooldown Evaluation ]

    Case A: Detached JWS Signature Present

    Parse compact JWS: header..signature

    Extract kid from protected header

    Lookup issuer public key from local VCI JWK cache

    Verify ECDSA P-256 (ES256) signature over Digest(LOINC || Result || SpecimenDate)

    IF Valid -> Assign Badge: LAB_VERIFIED_LEVEL_1

    BYPASS self-report cooldown timer

    IF Invalid -> REJECT: 401 Unauthorized

    Case B: No Lab Signature (Manual Self-Report)

    Query Redis for rate_limit:

    IF active cooldown found: REJECT 429 Too Many Requests (Retry-After header)

    IF cooldown clear: Assign Badge: COMMUNITY_SELF_REPORT_LEVEL_2

    Set Cooldown Timer (21-30 days)

    [ Step 4: Ephemeral Persistence ]

    → Write to Redis Cluster (ZADD manifest:active, EXPIRE ttl)

    → Append to cold audit log with rolling window deletion

    [ Response 201 Created ]

    Returns manifest_id, confidence_badge, expires_at, receipt_timestamp

    4. Stateless Memory Architecture (Redis + Cold Store)

    The bulletin board runs on a high-throughput, low-latency stateless memory architecture designed for fast concurrent client batch fetches:

    RELAY STORAGE INFRASTRUCTURE
    HOT TIER: In-Memory Redis 7.x Cluster
    - Active Manifests Sorted Set: ZADD manifests:by_time
    - Manifest Hashes Set: SADD manifest::hashes
    - Auto-Eviction: EXPIREAT manifest: (14-30d)
    - Replay Shield: SETNX pow:used: 1 EX 1800 (Prevents PoW reuse)
    COLD TIER: Stateless Rolling Database (PostgreSQL 16 / CockroachDB)
    - Table: public_manifests (manifest_id, loinc, tier, badge, expires_at, created_at)
    - Table: manifest_hashes (manifest_id, blake3_hash) - Clustered by published_at
    - Partitioning: Automated daily tables with DROP TABLE for partitions > 30 days old

    Automatic TTL & Partition Drop Automation:

  • Hot Tier (Redis): Every manifest key is assigned an explicit TTL matching the clinical transmission window (Tier 1: 30 days, Tier 2: 30 days, Tier 3: 45 days). Redis native volatile-ttl eviction guarantees zero stale hash retention.
  • Cold Tier (Database): Daily table partitions (e.g., manifest_hashes_2026_09_03). A scheduled cron worker runs DROP TABLE on any partition older than 30 days, guaranteeing that subpoena requests cannot yield historical data.

    • 5. Client Batch Polling & Blind Matching Contract

    The endpoint GET /manifest/batch serves client devices synchronizing exposure manifests in the background:

  • Incremental Synchronization: The client supplies ?since=. The relay queries the sorted set manifests:by_time for items where timestamp > since and returns up to limit entries (default 100, max 1000).
  • Next Cursor Token: The response includes next_since. If the client is caught up, manifests is empty and next_since equals the current server timestamp.
  • Decentralized Local Matching: The mobile client ingests the batch into volatile memory and performs a private set intersection against its local SQLite Ledger B (encounter_sessions). If an encounter matches:
  • The server is never notified.
  • The mobile OS triggers a local discreet notification.
